# ADR-007. Шаги сессии: сведения о шагах — поле лога, место остановки вычисляется

Статус: принято · 2026-10 · релиз 1.6 (FR-52…FR-66), задача З-1

## Контекст

В 1.5 шаги ориентира идут по часам: расписание живёт только в таймере (`meta.timer.stepMinutes`) и обнуляется при «Стоп», лог хранит только `durationMin` (`services/timer.service.ts`, `types/time-log.ts`). Релиз 1.6 (документ фичи v1.6, FR-52…FR-66) требует, чтобы шаг менял только владелец, «Стоп» сохранял минуты шагов, а следующая сессия топика стартовала с места остановки.

Что должно быть известно (документ фичи, «Данные и совместимость»):

- о сессии — минуты каждого шага, шаг старта, шаг остановки, продолжила ли круг, лимит, число шагов ориентира; сумма минут шагов равна минутам лога; у ручных логов и логов до 1.6 этих сведений нет;
- об идущей сессии — активный шаг, минуты шагов на текущий момент, продолжает ли круг; переживает перезагрузку, смена шага сохраняется ≤ 1 с;
- о месте остановки — шаг остановки, накопленное круга, пройден ли круг; всегда совпадает с тем, что следует из оставшихся логов: после правки, удаления, «Отменить» и импорта — как при расчёте заново.

НФТ: лог и минуты шагов записываются вместе или никак; уже прозвучавший сигнал шага не повторяется после перезагрузки; минуты шагов живут столько же, сколько лог; полный экспорт на 10 000 логов растёт не больше чем на 2 МБ; подсказки для «Сегодня» и быстрого выбора считаются ≤ 100 мс на 3000 топиков и 10 000 логов.

Как устроено сейчас (на это опирается решение):

- запись идёт через `DataStore` (ADR-002); несколько коллекций вместе — `DataStore.commit` одной транзакцией (AGENTS.md);
- «Объединить» сливает каждую коллекцию отдельно, по записи с большим `updatedAt` (`mergeEntities`);
- удаление лога — сразу удаление записи; «Отменить» в течение 10 с возвращает её копию из памяти (`LogsService.remove`, `ProgramService.remove`). `deletedAt` в коде только читается: мягкого удаления и очистки через 30 дней нет;
- версия базы IndexedDB — 2 (`DB_VERSION`), схема снимков — 4 (`SCHEMA_VERSION`);
- 1.5 сохраняет неизвестные поля записей: правка лога — `{ ...log, ...patch }`, нормализация таймера — `{ ...meta.timer, … }`.

## Варианты

Критерии: лог и шаги атомарны; место совпадает с логами после правки, удаления, «Отменить», «Заменить» и «Объединить»; 1.5 открывает данные после отката; объём изменений и общие файлы задач одной волны; отклик.

### 1. Где лежат сведения FR-56 о сессии

| Критерий | A. Поле `steps` в логе | B. Коллекция `logSteps`, ключ — id лога |
|---|---|---|
| Запись вместе с логом | одна запись — атомарна сама по себе | две коллекции — `DataStore.commit` в каждом месте записи: «Стоп», правка, удаление, «Отменить» |
| «Отменить» удаление | копия лога в памяти возвращает и шаги | нужно хранить и возвращать две записи |
| «Объединить» | шаги едут со своим логом, побеждает вся запись | коллекции сливаются отдельно: лог из одного файла и шаги из другого — сумма шагов ≠ минутам лога, после удаления остаются сироты |
| IndexedDB | новое хранилище не нужно, версия базы 2 | новое хранилище, версия базы 3: 1.5 после отката не откроет базу (`openDB` с меньшей версией — `VersionError`) |
| Экспорт | ≈ 160–190 байт на лог с шагами | столько же и ещё id лога, `createdAt`, `updatedAt` |
| Файлы | `types/`, `storage/snapshot.ts` | ещё адаптеры, `COLLECTIONS`, запись в сервисах через `commit` |

Отброшен сразу вариант C — словарь «id лога → шаги» в `meta`: одна запись растёт с каждой сессией, а «Объединить» заменяет `meta` целиком и теряет шаги одной из сторон.

### 2. Место остановки хранится или считается по логам

| Критерий | A. Считается доменом по учитываемым логам, как план (ADR-003) | B. Хранится у топика (`item`) или в `meta`, обновляется при каждом изменении логов |
|---|---|---|
| Совпадение с логами | по построению: после любой правки, удаления, «Отменить» и импорта — тот же расчёт | обновлять в «Стоп», правке, удалении, «Отменить», смене типа лога, «Заменить», «Объединить»; после «Объединить» место из одного файла и логи из другого расходятся — всё равно нужен пересчёт |
| Другие данные | не трогает | запись в `item` меняет его `updatedAt`: «Объединить» программы и обновление курса (ADR-005) начинают зависеть от сессий |
| Отклик | один проход по логам в памяти, без хранилища; порог ≤ 100 мс проверяют тесты З-6 и З-9 | чтение готового значения |
| Код | одно правило в домене | правило и синхронизация кэша во всех местах записи |

### 3. Что держит идущий таймер

| Критерий | A. Расписание 1.5 (`stepMinutes`) | B. Мс по шагам и активный шаг (`ITimerSteps`) | C. Журнал смен шага: шаг и момент каждой смены |
|---|---|---|---|
| Ручная смена шага (FR-52) | нет: шаг выводится из прошедшего времени | да | да |
| Минуты шага | план, а не факт | факт: `spentMs` и текущий отрезок активного шага | факт, суммой по журналу |
| Размер | n чисел | n чисел и флаги | растёт с каждой сменой |
| Сумма шагов = часы сессии | нет | всегда, по построению | всегда |

Накопленное прошлых сессий круга таймер не копирует: оно считается по логам круга. Копия в таймере расходилась бы с логами после правки или удаления лога во время сессии.

## Решение

1A, 2A, 3B: сведения о шагах — поле лога, место остановки и накопленное считаются по логам, таймер держит миллисекунды по шагам и активный шаг. Круг различается идентификатором `circleId`, который сессия получает при старте.

### Модель данных

Типы — `src/app/types/` (экспорт через `types/index.ts`):

| Тип | Поле | Что хранит |
|---|---|---|
| `ITimeLog` | `steps?: ILogSteps \| null` | шаги сессии; `null` или нет поля — «без шагов» |
| `ILogSteps` (`log-steps.ts`) | `minutes` | целые минуты каждого шага за сессию по индексу с 0; сумма = `durationMin`; длина ≥ `stepCount` |
| | `startIndex`, `stopIndex` | шаг старта и шаг остановки |
| | `continuesCircle` | стартовала с подсказкой «Продолжить…» |
| | `circleId` | круг, в который сессия добавила минуты |
| | `limitMin` | лимит — длина при старте (FR-55) |
| | `stepCount` | число шагов ориентира при старте |
| `ITimerState` | `steps?: ITimerSteps \| null` | шаги идущей сессии; `null` — сессия без шагов |
| | `legacySchedule?: boolean` | таймер запущен до 1.6 и ещё не переведён (FR-65) |
| | `plannedMin` (есть) | лимит сессии с шагами — длина, переданная точкой старта |
| | `stepMinutes` (есть) | расписание 1.5; в 1.6 только читается при переводе |
| `ITimerSteps` (`timer-steps.ts`) | `activeIndex` | активный шаг |
| | `spentMs` | мс без пауз, отданные каждому шагу до последней смены; активному шагу сверх этого идёт `elapsed − Σ spentMs` (не меньше 0) |
| | `startIndex`, `continuesCircle`, `circleId`, `stepCount` | как в `ILogSteps`; при «Стоп» переходят в лог |
| | `planSignaled` | шаги, которым сигнал «Время шага по плану вышло» в этой сессии больше не подаётся |
| | `limitSignaled` | «Время сессии вышло» уже прозвучало |

Новые поля в типе необязательные, а не обязательные с умолчанием, как в прошлых схемах. Обязательное поле ломает сборку в файлах других задач: лог создают `services/logs.service.ts` (З-8) и `domain/test-fixtures.ts` (З-6), таймер — `services/timer.service.ts` (З-8). После нормализации (З-4) поля есть всегда; запись держит контракт сервиса: черновик `LogsService.create` требует `steps`, `TimerService.start` пишет `steps` и `legacySchedule: false` (З-8). Читатель понимает отсутствие поля как «без шагов».

Шаг — индекс в `guide.steps` с 0: у шага нет ключа (Д-10). Шаг, добавленный в ориентир во время сессии, получает свой индекс, массивы удлиняются. Если активного шага больше нет, активным становится последний (FR-63). Сессия, начатая без шагов ориентира, остаётся без шагов до «Стоп», даже если ориентир у топика появился во время неё [ДОПУЩЕНИЕ: случай не описан в FR-52…FR-66].

### Что восстанавливается по модели

| Что должно быть известно | Откуда |
|---|---|
| Минуты каждого шага сессии | `log.steps.minutes` |
| Шаг старта, шаг остановки | `startIndex`, `stopIndex` |
| Продолжила ли круг | `continuesCircle` |
| Лимит | `limitMin` |
| Число шагов на момент сессии | `stepCount` — при старте [ДОПУЩЕНИЕ: «на момент сессии» = при старте; ориентир, изменённый во время сессии, даёт следующей сессии новый круг по FR-63] |
| Ручной лог, лог до 1.6 | `steps: null` |
| Активный шаг, минуты на текущий момент, продолжает ли круг | `timer.steps`: `activeIndex`, `spentMs` и `elapsed`, `continuesCircle` |
| Место остановки: шаг, накопленное, пройден ли круг | расчёт домена по учитываемым логам (ниже) |
| Период повторяющегося топика | день начала лога (`startedAt`, граница дня), `challenge.startDate`, `routeBlocks`, `item.routeRole`, `item.recurrenceWeeks` — уже в данных |

### Правила расчёта (домен, З-6)

1. Учитываемый лог (FR-57, FR-60, FR-62, FR-65): `source: 'timer'`, тип «Учёба» или «Практика», `steps` не `null`, нет `deletedAt`, у топика нет дня контрольной (`checkpointDay`).
2. Последний учитываемый лог топика — по `startedAt`, как `DataStore.logs` [ДОПУЩЕНИЕ: порядок по началу сессии].
3. Круг — учитываемые логи топика с тем же `circleId`, что у последнего; у повторяющегося топика — только в периоде последнего лога (FR-61). Накоплено шага i — сумма `minutes[i]` логов круга. Шаг остановки — `stopIndex` последнего лога. Круг пройден, если шаг остановки последний и его накопленное не меньше плана (FR-59). План берётся из текущего ориентира (FR-63).
4. Минуты шагов лога читаются одной функцией: если их сумма не равна `durationMin` (лог правили в 1.5 после отката), разница раскладывается правилом Д-7.
5. Шаг старта и вид подсказки — восемь правил FR-58 в одной функции. Её зовут и таймер (З-8), и подсказка (З-9) — Д-27. Продолжение круга даёт `continuesCircle: true` и `circleId` места. Новый круг даёт `false` и новый `circleId` (`createId()` в сервисе, домен остаётся чистым).
6. «Стоп»: мс шагов переводятся в целые минуты с суммой `round(elapsed / 60 000)` — минутами лога, как в `stop` 1.5 — методом наибольшего остатка. Если засчитано другое число («Засчитать», «Сколько засчитать?»), разница раскладывается по Д-7.
7. Правка минут лога (FR-64): разница между новой `durationMin` и текущей суммой шагов раскладывается по Д-7. Начало, сдвинутое без смены длины, шагов не меняет.
8. Перевод таймера 1.5 (FR-65) — ниже.

Удаление первого лога круга убирает только его минуты: остальные сессии круга остаются в нём по `circleId`. Счёт по цепочке флагов `continuesCircle` в этом случае приклеил бы их к прошлому, уже закрытому кругу [ДОПУЩЕНИЕ: так читается «как если бы сессии не было» FR-64 для лога в середине истории].

### Миграция схемы 4 → 5 (З-4)

Только добавление полей с умолчанием, ничего не удаляется и не переименовывается:

- `SCHEMA_VERSION = 5`, комментарий «5 — шаги сессии (1.6)»;
- `normalizePartial`: у логов `steps: log.steps ?? null`; у таймера `steps: timer.steps ?? null`, `legacySchedule: timer.legacySchedule ?? true`. Таймер без поля записан до 1.6;
- нормализация идёт при каждой загрузке и импорте, без немедленной перезаписи хранилища (как 3 → 4). Запись получает поля, когда её перепишут;
- `checkSnapshot` принимает схемы 1–5. Битые сведения отклоняются с путём поля, данные не меняются:
  - `timeLogs[i].steps` — `null` или объект: `minutes` — непустой массив целых ≥ 0; `startIndex` и `stopIndex` — целые в пределах `minutes`; `stepCount` — целое от 1 до длины `minutes`; `limitMin` — конечное число > 0; `continuesCircle` — boolean; `circleId` — непустая строка; у такого лога `source: 'timer'` и `itemId` не `null`;
  - `meta[i].timer` — `null` или объект, у которого `steps` — `null` или объект: `activeIndex` — целое в пределах `spentMs`; `spentMs` — массив конечных чисел ≥ 0; `startIndex` — целое ≥ 0; `stepCount` — целое ≥ 1; `planSignaled` — массив целых ≥ 0; `continuesCircle` и `limitSignaled` — boolean; `circleId` — строка; `legacySchedule` — boolean или нет поля;
  - сумма `minutes` с `durationMin` не сверяется: лог, исправленный в 1.5 после отката, законно расходится, и экспорт такого лога должен импортироваться. Домен выравнивает его правилом 4.

### Версия базы IndexedDB

Не меняется — `DB_VERSION = 2`: новых хранилищ нет, поля лежат в записях `timeLogs` и `meta`, а IndexedDB не проверяет их состав. `indexeddb.adapter.ts`, `memory.adapter.ts` и `COLLECTIONS` не меняются.

### Совместная запись лога и шагов

- Лог и его шаги — одна запись: любой `put` лога атомарен, отдельной транзакции для шагов не нужно. Правка — `upsert` той же записи с новыми `durationMin` и `steps.minutes`.
- «Стоп», «Переключиться» и «Засчитать» пишут лог и очистку таймера (`meta.timer = null`) одной транзакцией `DataStore.commit` — это две коллекции (AGENTS.md). Закрытие вкладки во время «Стоп» оставляет либо идущий таймер со всеми шагами, либо лог с шагами и без таймера. Нет ни лога без шагов, ни потерянной сессии, ни второго лога той же сессии.
- Порядок в З-8: черновик конспекта привязывается к id лога (`SessionDraftService.attach`) до `commit`, и `meta` для пакета берётся уже после этого. Пока `commit` не завершён, `updateMeta` не вызывается: иначе очередь `DataStore` запишет `meta` с ещё не очищенным таймером. «Переключиться» стартует новую сессию после завершения `commit`. При отказе хранилища `commit` ничего не меняет в памяти: таймер идёт дальше, ошибку показывает тост.
- Смена шага и сигналы — `updateMeta` таймера. Запись уходит сразу, без задержки (≤ 1 с — НФТ «Надёжность»).

### Удаление, «Отменить» и очистка через 30 дней

- Шаги удаляются вместе с записью лога: `LogsService.remove` и каскад `ProgramService.remove` не меняются. «Отменить» возвращает копию лога из памяти вместе с шагами. Место пересчитывается само: после удаления — как без этой сессии, после «Отменить» — как до удаления.
- Мягкого удаления и очистки через 30 дней в коде 1.5 нет: удалённый лог исчезает из хранилища сразу. Если удаление станет мягким, шаги уйдут вместе с записью при очистке, а лог с `deletedAt` место не задаёт (правило 1). [НУЖНЫ ДАННЫЕ: вводить ли в 1.6 мягкое удаление логов с очисткой через 30 дней, на которое ссылаются НФТ «Хранение» и «Готово, когда» З-4, или считать достаточным удаление вместе сразу — владелец. От ответа зависят объём З-4 и `LogsService.remove` в З-8; модель этого ADR не зависит.]

### Импорт «Заменить» и «Объединить»

- «Заменить»: логи приходят со своими `steps`, место считается по ним. Тот же файл в чистом браузере даёт те же подсказки и минуты шагов (FR-66, US-32, критерий 3).
- «Объединить»: `mergeEntities` берёт запись лога целиком, шаги не отделяются от своего лога. Место считается по объединённым логам: сессии двух браузеров одного круга складываются по `circleId`, шаг остановки — у последнего по `startedAt`.
- Файлы схем 1–4: логи получают `steps: null` (FR-65), таймер — `legacySchedule: true`. Файл схемы 5 в 1.5 отклоняется (`schemaVersion` > 4), как при прошлых изменениях схемы.
- Импорт программы (`kind: 'program'`) логов не содержит и не меняется. CSV-экспорт не меняется.

### Таймер, запущенный до 1.6 (FR-65)

- Признак — `legacySchedule: true`: нормализация ставит его таймеру без поля. Нормализация только добавляет поля и не знает часов, поэтому перевод в ней не делается.
- Перевод — чистая функция домена (З-6). Вызывает её `TimerService` (З-8) при первом открытии таймера с `legacySchedule: true` и сразу пишет результат в `meta.timer` с `legacySchedule: false`.
- Правило: расписание = `stepMinutes`, если его длина равна числу шагов ориентира, иначе плановые минуты шагов — как `buildGuidePhases` в 1.5. Активный шаг — шаг расписания на текущий `elapsed`, с тем же допуском, что `phaseIndex` в 1.5. Шагам до него — их минуты расписания, активному — остаток до `elapsed`, остальным — 0. `startIndex: 0`, `continuesCircle: false`, новый `circleId`, `stepCount` — число шагов ориентира сейчас. Лимит — сохранённый `plannedMin`.
- Сигналы: в `planSignaled` — шаги, уже набравшие план, `limitSignaled` — если `elapsed` уже не меньше лимита [ДОПУЩЕНИЕ: сигнал, который мог прозвучать в 1.5 до обновления, после перевода не повторяется — по Д-21].
- У топика без шагов ориентира перевод даёт `steps: null`.

### Метрики (вход для З-5)

По модели без самоотчёта видны:

- сессии с подсказкой «Продолжить с шага N» — `continuesCircle` и `startIndex`;
- минуты каждого шага; лимит и превышение — `durationMin − limitMin`;
- закрытый круг — следующая учитываемая сессия топика с другим `circleId`.

Порядок шагов внутри сессии не хранится. Поэтому «первый шаг, получивший минуты» однозначен, только когда минуты есть у одного шага или у шага N их нет. План шагов на момент сессии тоже не хранится, драйвер «шаги без недобора» берёт текущий ориентир. [НУЖНЫ ДАННЫЕ: достаточно ли этого для основной метрики и драйвера или в FR-56 нужен ещё «первый шаг с минутами» и план шагов — владелец, по итогу З-5. Если нужен, это ещё одно поле `ILogSteps`: тип и проверку добавляет З-4, запись — З-8, остальная модель не меняется.]

## Цена отказа

- От 1B: отдельная коллекция дала бы шагам свою историю записи, но потребовала бы `commit` во всех местах записи, разошлась бы с логом при «Объединить» и сменила бы версию базы. Откат на 1.5 тогда не открывает данные вовсе.
- От 2B: подсказка не читается готовой, а считается при изменении логов, ориентиров и топиков. Пересчёт идёт по сигналам данных, а не по тику таймера (З-9), порог отклика держат тесты.
- От 3A и 3C: расписание 1.5 остаётся только для перевода старого таймера. Истории смен шага внутри сессии нет — см. «Метрики».
- Цена выбранного:
  - поля в типах необязательные, поэтому запись без `steps` ловят тесты и контракт сервиса, а не компилятор;
  - `circleId` — около 50 байт на лог. Оценка экспорта: 160–190 байт на лог с шагами, на 10 000 таких логов — до 1,9 МБ при пороге 2 МБ; замер — З-4;
  - логи, исправленные в 1.5 после отката, читаются через выравнивание по Д-7, а не как записаны.

## Откат

Схема 5 только добавляет поля, версия базы IndexedDB не меняется. Поэтому 1.5 после отката открывает базу и сохраняет неизвестные поля записей. Это ожидание проверяет З-12 (Н-6, О-4).

Последствия работы в 1.5 после отката и возврата на 1.6:

- лог, исправленный в 1.5, хранит старые минуты шагов — домен выравнивает их по Д-7 (правило 4);
- лог, удалённый в 1.5, ушёл вместе с шагами;
- сессия, записанная в 1.5, — «без шагов» и места не задаёт;
- таймер, запущенный в 1.6 и продолженный в 1.5, сохраняет `steps`: после возврата время с последней смены шага в 1.6 достаётся активному шагу 1.6;
- таймер, запущенный в 1.5, переводится при первом открытии.

Экспорт 1.6 в 1.5 не импортируется (схема 5). Откат релиза — `git revert` по README и импорт копии, скачанной до обновления.
